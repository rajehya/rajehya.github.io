Executive Summary

This project demonstrates the complete deployment of an enterprise-grade Microsoft Active Directory infrastructure built entirely within a virtual environment using VMware Workstation.

The objective was not simply to install Active Directory, but to design a structured enterprise identity infrastructure following Microsoft administration and security best practices.

The environment was built around a dedicated Active Directory forest named yasserteach.local, with DC01 serving as the primary Domain Controller and DNS Server.

The project includes:

  • Enterprise network configuration

  • Active Directory Domain Services deployment

  • DNS integration

  • Organizational Unit (OU) design

  • Enterprise user provisioning

  • PowerShell automation

  • Security Group administration

  • Role-Based Access Control (RBAC)

  • AGDLP implementation

  • Enterprise SMB File Shares

  • NTFS permission management

  • Least Privilege implementation

Rather than assigning permissions directly to users, access is managed through layered Security Groups and Domain Local Groups using Microsoft's AGDLP model.

PowerShell automation was incorporated throughout the deployment to automate repetitive administrative tasks, improve consistency, and demonstrate enterprise Windows administration capabilities.

The completed infrastructure closely resembles a production Active Directory environment and demonstrates practical experience expected from Windows Server Administrators, Infrastructure Engineers, and Enterprise Systems Engineers.

2. Infrastructure Deployment

This phase documents the deployment of the core infrastructure used throughout the project. The environment was built from the ground up, beginning with virtual networking, followed by Windows Server preparation, Active Directory installation, and finally the deployment of the yasserteach.local domain.

The primary objective of this phase was to establish a stable, secure, and scalable identity infrastructure capable of supporting enterprise authentication and centralized administration.

2.1 Configuring the Virtual Network Infrastructure

The project began by configuring an isolated virtual network using VMware Workstation Virtual Network Editor.

A dedicated Host-Only network was created to ensure that all virtual machines communicate exclusively within the laboratory environment without relying on external DHCP or Internet connectivity.

The isolated network serves as the communication backbone for the following systems:

  • DC01

  • W11-01

This configuration provides complete administrative control over IP addressing, DNS resolution, and Active Directory communication.

Why This Matters

Enterprise Active Directory environments should always be deployed on a predictable and controlled network where infrastructure services are isolated from production traffic.

2.2 Preparing Windows Server

After installing Windows Server 2022, the initial server configuration was performed using Server Manager.

This phase verifies that the operating system is healthy before installing enterprise roles.

Initial validation included:

  • Local Server status

  • Computer information

  • Windows Updates

  • Time configuration

  • Network adapter status

  • Remote management

Server Manager provides centralized administration for Windows Server infrastructure and becomes the primary management console throughout the project.

2.3 Renaming the Enterprise Server

The default computer name was replaced with DC01.

Using descriptive server names is considered an enterprise best practice because administrators can immediately identify the role of each system.

The naming convention used throughout this project is:

Server Purpose
DC01 Domain Controller
W11-01 Enterprise Client

As the infrastructure expands, future servers could include:

  • FS01 (File Server)

  • APP01 (Application Server)

  • SQL01 (Database Server)

Maintaining standardized naming conventions improves documentation, monitoring, troubleshooting, and operational consistency.

2.4 Configuring Static Network Settings

Before deploying Active Directory, DC01 was configured with a static IPv4 address.

Unlike client devices, infrastructure servers must maintain permanent IP addresses to guarantee that services such as DNS and Active Directory remain continuously available.

The configuration included:

  • Static IPv4 Address

  • Subnet Mask

  • Default Gateway

  • Preferred DNS Server

Since DC01 also hosts DNS, the DNS configuration points directly to the Domain Controller itself.

Best Practice

Microsoft recommends assigning static IP addresses to all Domain Controllers to prevent authentication failures caused by changing network addresses.

2.5 Validating Network Configuration

The command:

ipconfig /all

was executed to verify the network configuration before Active Directory installation.

Validation confirmed:

  • Computer Name = DC01

  • Correct IPv4 Address

  • Correct Subnet Mask

  • Correct DNS Server

  • Active Network Adapter

Verifying network configuration before deploying Active Directory reduces deployment issues and ensures reliable communication between infrastructure services.

2.6 Installing Active Directory Domain Services

The Active Directory Domain Services (AD DS) role was installed using Server Manager.

During the same installation process, the DNS Server role was also deployed because Active Directory relies heavily on DNS for locating Domain Controllers and other directory services.

The deployment transforms Windows Server from a standalone operating system into the foundation of an enterprise identity infrastructure.

Installed Roles

Role Purpose

2.7 Promoting DC01 to a Domain Controller

Following the successful installation of AD DS, DC01 was promoted to a Domain Controller.

This operation installs the Active Directory database, SYSVOL, authentication services, and replication components required to manage enterprise identities.

Once promotion is complete, DC01 becomes responsible for:

  • User Authentication

  • Computer Authentication

  • Kerberos

  • LDAP

  • Group Policy Processing

  • DNS Integration

This represents the transition from a standalone server to an enterprise identity server.

2.8 Creating the Active Directory Forest

A new Active Directory forest named:

yasserteach.local

was created as the root of the enterprise directory infrastructure.

This forest contains:

  • Domain Controller (DC01)

  • Active Directory Database

  • Authentication Services

Using a dedicated forest provides centralized identity management for all users, computers, groups, and enterprise resources.

The validation confirmed that:

Successful validation indicates that the server is ready to host enterprise directory services.

4. Security Groups and Role-Based Access Control (RBAC)

After completing the Active Directory organizational structure and provisioning enterprise user accounts, the next phase focused on implementing Role-Based Access Control (RBAC).

Rather than assigning permissions directly to user accounts, Global Security Groups were created to represent organizational departments. This approach simplifies permission management, improves scalability, and aligns with Microsoft's recommended enterprise administration practices.

The implementation also prepared the infrastructure for the AGDLP model by separating user administration from resource permission management.

4.1 Creating Enterprise Global Security Groups

Dedicated Global Security Groups were created for each department within the yasserteach.local domain.

Each Global Group represents a business department and is responsible for holding user memberships only. No permissions are assigned directly to these groups.

The following naming convention was implemented:

Security Group Department
GG_IT Information Technology
GG_HR Human Resources
GG_Finance Finance
GG_Operations Operations
GG_Executives Executive Management

The GG prefix represents Global Group, making it immediately identifiable within the Active Directory environment.

Why Global Groups?

Global Groups should contain users from the same domain and represent organizational roles rather than resource permissions.

This separation improves long-term administration and follows Microsoft's recommended Active Directory design.

4.2 Implementing Role-Based Access Control

The GG_IT Global Security Group was created to represent all users belonging to the Information Technology department.

Instead of assigning permissions directly to IT users, permissions will later be granted to the group itself, allowing all members to inherit the required access automatically.

This implementation follows the principle of Role-Based Access Control (RBAC), where access is granted according to job responsibilities rather than individual identities.

Benefits

  • Simplified permission management

  • Reduced administrative effort

  • Easier auditing

  • Consistent access control

  • Faster onboarding and offboarding

4.3 Validating Security Group Configuration

After creating the Global Security Groups, each group was reviewed to verify that it had been created successfully within the Corporate Organizational Unit.

The validation process confirmed that the groups were available for future membership assignments and permission delegation.

4.4 Assigning Users to Security Groups

Enterprise users were assigned to the appropriate Global Security Groups based on their department.

Examples include:

  • IT users → GG_IT

  • HR users → GG_HR

  • Finance users → GG_Finance

  • Operations users → GG_Operations

  • Executive staff → GG_Executives

This approach ensures that future permission changes only require modifying group membership instead of changing permissions on individual user accounts.

Enterprise Best Practice

Never assign permissions directly to user accounts.

Always assign permissions to Security Groups.

4.5 Verifying Group Membership

Group membership was verified after users were assigned to their respective Global Security Groups.

This validation confirms that all users will inherit permissions through their department group once resource access is configured.

Successful membership verification is an important step before implementing AGDLP.

5. Enterprise File Services and AGDLP Implementation

After implementing Global Security Groups and Role-Based Access Control (RBAC), the next phase focused on securing enterprise file services using Microsoft's recommended AGDLP model.

Rather than assigning NTFS permissions directly to users or Global Groups, dedicated Domain Local Groups were introduced to separate identity management from permission management.

This design provides a scalable, maintainable, and secure access control model suitable for enterprise environments.

5.1 Creating Domain Local Security Groups

To implement Microsoft's AGDLP model, dedicated Domain Local Security Groups were created to manage access to enterprise file resources.

Unlike Global Groups, which contain user accounts, Domain Local Groups are responsible only for holding permissions assigned to folders and shared resources.

The following Domain Local Groups were created:

Domain Local Group Purpose
DL_Finance_RW Finance Folder (Read/Write)
DL_HR_RW HR Folder (Read/Write)
DL_IT_RW (إذا موجود) IT Folder (Read/Write)
DL_Operations_RW (إذا موجود) Operations Folder (Read/Write)
DL_Executives_RW (إذا موجود) Executive Folder (Read/Write)

The DL prefix identifies the group as a Domain Local Security Group, while the RW suffix indicates Read/Write access.

5.2 Implementing Microsoft's AGDLP Model

The project implements Microsoft's recommended AGDLP architecture.

Instead of granting permissions directly to users, Global Security Groups were nested inside Domain Local Groups.

The implementation follows this structure:

Domain Users

│

▼

GG_Finance

│

▼

DL_Finance_RW

│

▼

Finance Folder

│

▼

Modify Permission

This layered design separates identity management from permission management, making future administration significantly easier.

For example:

  • Finance employees become members of GG_Finance.

  • GG_Finance becomes a member of DL_Finance_RW.

  • DL_Finance_RW receives Modify permission on the Finance folder.

If a new Finance employee joins the company, the administrator only needs to add the user to GG_Finance. No folder permissions need to be modified.

5.3 Automating AGDLP with PowerShell

PowerShell was used to automate the nesting of Global Groups into Domain Local Groups.

The following PowerShell cmdlet was used:

Add-ADGroupMember

Instead of manually configuring every relationship, PowerShell provides a faster and more consistent deployment process.

Automation ensures that every department follows the same permission model while reducing administrative effort.

This structure simplifies administration while keeping business data logically separated.

5.5 Publishing Enterprise SMB Shares

After creating the departmental folder structure, the root share was published using Microsoft's SMB file sharing service.

Publishing the shared folder allows authenticated domain users to access centralized resources across the yasserteach.local domain.

At this stage, access is still controlled by NTFS permissions rather than Share Permissions alone.

Enterprise environments typically grant broad Share Permissions while relying on NTFS permissions for detailed security enforcement.

5.6 Configuring NTFS Security Permissions

NTFS permissions were configured using Domain Local Security Groups instead of assigning permissions directly to individual users.

This design greatly simplifies permission management.

Instead of adding dozens of Finance users to the Finance folder, only the DL_Finance_RW group receives the required permissions.

Every Finance employee automatically inherits access through group membership.

5.7 Removing Permission Inheritance

Permission inheritance was disabled on departmental folders before assigning explicit permissions.

Removing inherited permissions prevents accidental access inherited from parent directories and allows each department to have an independent security configuration.

This step significantly improves security by ensuring that only explicitly authorized groups receive access.

5.8 Assigning Domain Local Groups to NTFS

The DL_Finance_RW group was assigned directly to the Finance folder.

This represents the final stage of Microsoft's AGDLP model.

The resulting permission flow becomes:

User

↓

GG_Finance

↓

DL_Finance_RW

↓

Finance Folder

↓

Modify Permission

No permissions are assigned directly to users.

This approach greatly simplifies permission management throughout the enterprise.

5.9 Applying the Principle of Least Privilege

Rather than granting Full Control, departmental groups were granted only Modify permissions.

The Modify permission allows users to:

  • Read files

  • Create files

  • Modify files

  • Delete files

while preventing unnecessary administrative privileges.

Implementing the Principle of Least Privilege reduces the organization's attack surface and minimizes the impact of compromised user accounts.

5.10 Automating NTFS Permissions

PowerShell together with the icacls utility was used to automate NTFS permission assignment.

The automation applies identical permission structures across departmental folders while ensuring consistency.

Using icacls also allows administrators to export, verify, and recreate permissions whenever necessary.

5.11 Validating NTFS Permissions

After configuring NTFS permissions, the icacls command was used to verify that every departmental folder had received the intended permissions.

The validation confirmed that:

  • DL_Finance_RW was assigned correctly.

  • Permission inheritance was removed.

  • Modify permissions were applied successfully.

  • Access control matched the AGDLP design.

Starting from an isolated VMware virtual network, the project progressed through the deployment of DC01, the creation of the yasserteach.local forest, the design of a structured Organizational Unit hierarchy, enterprise user provisioning, Security Group implementation, Role-Based Access Control (RBAC), AGDLP permission management, centralized SMB file sharing, NTFS security, and PowerShell automation.

Unlike a basic Active Directory installation, this implementation emphasizes scalability, maintainability, and security by separating identity management from permission management and automating repetitive administrative tasks.

The resulting infrastructure closely reflects a real-world enterprise deployment and demonstrates practical skills expected from Windows Server Administrators, Infrastructure Engineers, and Systems Engineers responsible for managing Microsoft-based enterprise environments.
