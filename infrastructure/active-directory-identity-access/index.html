Project Overview

This project demonstrates the deployment of a Microsoft Active Directory identity and access environment in a virtual lab using VMware Workstation and Windows Server 2022.

The environment was built around the yasserteach.local forest, with DC01 providing Active Directory Domain Services and integrated DNS. The implementation extends beyond a basic domain installation by introducing a structured OU design, departmental user administration, Security Groups, the AGDLP access model, SMB file sharing, NTFS permissions, and PowerShell automation.

Access to departmental resources is managed through group membership rather than direct user permission assignments, making the configuration easier to maintain, audit, and scale.

Business Scenario

A fictional organization requires centralized identity management for multiple departments while maintaining consistent authentication, structured administration, and controlled access to shared resources.

Active Directory Domain Services was selected to centralize user and computer identities, while Security Groups and the AGDLP model were used to separate organizational roles from resource permissions.

The solution provides centralized authentication and authorization, department-based administration, group-based access control, PowerShell automation, SMB file sharing, and NTFS permission management.

2. Infrastructure Deployment

This phase establishes the foundation of the lab: virtual networking, Windows Server preparation, static network configuration, AD DS installation, DNS integration, and creation of the yasserteach.local forest.

2.1 Configuring the Virtual Network Infrastructure

The project began by configuring an isolated virtual network in VMware Workstation. The lab network allows the Domain Controller and Windows client to communicate within a controlled environment without depending on an external DHCP service.

The core systems connected to this network are DC01 and W11-01. This provides predictable control over IP addressing, DNS resolution, and Active Directory communication.

2.2 Preparing Windows Server

After installing Windows Server 2022, the initial server configuration was reviewed in Server Manager before installing directory services.

  • Computer information

  • Windows Update status

  • Time configuration

  • Network adapter status

  • Remote management

2.3 Renaming the Server

The default Windows Server computer name was replaced with DC01, using a role-based naming convention that makes the server's purpose immediately recognizable.

SystemPurpose
DC01Domain Controller / DNS Server
W11-01Domain Client

2.4 Configuring Static Network Settings

Before deploying Active Directory, DC01 was configured with a static IPv4 address. Stable addressing is important for infrastructure services because domain clients must be able to locate DNS and the Domain Controller consistently.

The server configuration included the IPv4 address, subnet mask, gateway as required by the lab network, and a DNS configuration that resolves through the Domain Controller.

2.5 Validating Network Configuration

The ipconfig /all command was used to verify the server name, IPv4 configuration, subnet, DNS settings, and active network adapter before Active Directory deployment.

2.6 Installing Active Directory Domain Services

The Active Directory Domain Services (AD DS) role was installed first through Server Manager.

During the subsequent Domain Controller promotion, DNS Server was selected and configured as part of creating the new forest. Active Directory relies on DNS service records to allow domain members to locate Domain Controllers and directory services.

RolePurpose
Active Directory Domain ServicesDirectory and identity services
DNS ServerAD-integrated name resolution and service discovery

2.7 Promoting DC01 to a Domain Controller

After the AD DS role was installed, DC01 was promoted to a Domain Controller. The promotion process configured the Active Directory database, SYSVOL, authentication services, Global Catalog functionality, and the components required for directory operations and future replication.

DC01 then became responsible for domain authentication, Kerberos, LDAP directory access, Group Policy processing, and DNS integration.

2.8 Creating the Active Directory Forest

A new forest named yasserteach.local was created, making it the root domain of the lab's Active Directory environment.

The deployment established the directory namespace, Active Directory database, authentication services, DNS integration, and the forest security boundary.

2.9 Active Directory Prerequisite Validation

Before installation completed, the Active Directory configuration wizard performed prerequisite checks to identify blocking issues with networking, DNS, or required dependencies.

The validation completed without blocking errors, allowing the Domain Controller promotion to continue.

2.10 Successful Domain Controller Deployment

After the automatic restart, DC01 started as the Domain Controller for yasserteach.local. Active Directory, DNS, and authentication services were then verified before proceeding with directory design.

4. Security Groups and Role-Based Access Control

Departmental Global Security Groups were created to represent organizational roles. This group-based model reduces direct permission assignments and prepares the directory for AGDLP.

4.1 Creating Global Security Groups

Security GroupDepartment
GG_ITInformation Technology
GG_HRHuman Resources
GG_FinanceFinance
GG_OperationsOperations
GG_ExecutivesExecutive Management

The GG prefix identifies each object as a Global Group and makes the naming convention easier to understand during administration and troubleshooting.

4.2 Implementing Group-Based Access Control

Users receive access according to departmental membership rather than through individually managed folder permissions. For example, IT users are members of GG_IT, while Finance users are members of GG_Finance.

This approach supports simpler onboarding, offboarding, auditing, and permission changes.

4.3 Validating Security Group Configuration

The Global Security Groups were reviewed after creation to verify their scope, type, naming, and location within the directory.

4.4 Assigning Users to Security Groups

  • IT users → GG_IT

  • HR users → GG_HR

  • Finance users → GG_Finance

  • Operations users → GG_Operations

  • Executive users → GG_Executives

For scalable administration, resource permissions are preferably assigned to Security Groups rather than maintained individually for each user account.

4.5 Verifying Group Membership

Membership was verified to ensure users were associated with the correct departmental role before resource permissions were introduced.

4.6 Reviewing the Security Group Structure

The completed Global Group structure represented the five departmental roles used throughout the lab and served as the identity layer of the AGDLP model.

4.7 Automating Group Membership with PowerShell

PowerShell was used to automate group membership with Add-ADGroupMember, reducing repetitive GUI work and improving consistency.

4.8 Managing Department Membership

Departmental memberships were reviewed after automation to confirm that each account inherited access through the intended role group.

4.9 Creating Department Resource Groups

Domain Local Security Groups were introduced as the permission layer for departmental resources. A consistent naming convention was used:

Prefix / SuffixMeaning
GGGlobal Group
DLDomain Local Group
RWRead / Write access

For example, DL_Finance_RW represents the Domain Local Group used for Finance read/write access.

4.10 Automating Active Directory Administration

PowerShell automation was extended beyond user provisioning to group creation, group membership, and AGDLP nesting. Combining graphical administration with scripting provides both visibility and repeatability during deployment.

5. Enterprise File Services and AGDLP Implementation

The next phase applied the AGDLP model to departmental SMB resources. Global Groups represented user roles, while Domain Local Groups represented resource permissions.

5.1 Creating Domain Local Security Groups

Domain Local GroupPurpose
DL_IT_RWIT Folder — Read / Write
DL_HR_RWHR Folder — Read / Write
DL_Finance_RWFinance Folder — Read / Write
DL_Operations_RWOperations Folder — Read / Write
DL_Executives_RWExecutives Folder — Read / Write

5.2 Implementing the AGDLP Model

Account
  ↓
GG_Finance
  ↓
DL_Finance_RW
  ↓
Finance Folder
  ↓
Modify Permission

Finance users are added to GG_Finance. That Global Group is nested into DL_Finance_RW, and the Domain Local Group receives the folder permission. A new Finance employee therefore only needs the correct group membership; the NTFS ACL does not need to be edited for every user.

5.3 Automating AGDLP with PowerShell

Add-ADGroupMember was used to automate the nesting of Global Groups into their corresponding Domain Local Groups.

5.4 Designing the Departmental File Structure

D:\Shares
├── Finance
├── HR
├── IT
├── Operations
└── Executives

The folder structure separates departmental data and provides a clear resource target for each Domain Local Group.

5.5 Publishing SMB Shares

The departmental repository was published using SMB so authenticated domain users could access shared resources across the lab network.

Share permissions and NTFS permissions work together; the effective network access is constrained by both layers. Detailed departmental authorization in this lab is enforced primarily through the NTFS ACL design.

5.6 Configuring NTFS Security Permissions

NTFS permissions were assigned to Domain Local Groups instead of individual users. This keeps resource ACLs stable even when employees join, leave, or change departments.

5.7 Controlling Permission Inheritance

Inheritance was disabled where required so departmental folders could use explicit ACLs appropriate to their access requirements. This provides clearer administrative boundaries and avoids unintended permissions inherited from a parent folder.

5.8 Assigning Domain Local Groups to NTFS

DL_Finance_RW was assigned to the Finance folder, completing the Accounts → Global → Domain Local → Permissions flow used by AGDLP.

5.9 Applying Least Privilege

Departmental users were granted Modify rather than unnecessary Full Control. This supports normal file operations while avoiding administrative rights that are not required for the business task.

5.10 Automating NTFS Permissions

PowerShell and icacls were used to apply and verify repeatable NTFS permission settings across departmental folders.

5.11 Validating NTFS Permissions

The final ACLs were reviewed to verify Domain Local Group assignment, inheritance settings, and Modify access.
